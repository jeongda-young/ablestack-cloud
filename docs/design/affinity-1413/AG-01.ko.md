# AG-01 / #1414 — Affinity 그룹 조회 범위와 비동기 완료 설계

상위 Epic #1413. 구현 브랜치 `dhslove/epic-1413-affinity-ui`.
기준: 최신 upstream/ablestack-europa `d9f068bbbba048313b6d38539651d19444c4d7c7` (2026-10-19 확인).
변경: UI와 집중 테스트. 백엔드 API/JAR·DB 스키마 변경 없음.

## 문제

- ChangeAffinity가 listAffinityGroups에 미지원 accountid를 전달해 타 계정 후보를 표시한다.
- updateVMAffinityGroup은 비동기 API인데 접수 직후 성공 알림과 닫기를 수행한다.
- 이전 재현은 최종 jobstatus=2/errorcode=530인데 UI가 성공을 표시했다. 기존 보고서와 실패 job은 Epic #1413에 보존했다.

## 조회 계약

| VM 소유 형태 | 조회 파라미터 |
| --- | --- |
| 계정 | account=VM 계정 이름, domainid=VM 도메인 |
| 프로젝트 | projectid=VM 프로젝트, domainid=VM 도메인 |
| 소유 정보 불완전 | 조회·제출 차단, VM 상세 재조회 안내 |

QueryManagerImpl은 소유자 ACL 검색과 도메인 공유 그룹의 사용 가능 범위를 결정한다. UI는 조회 결과의 system 계정 그룹을 임의로 제거하지 않는다. 이번 변경은 백엔드 권한 검사를 우회하거나 새 도메인 공유 유형을 만들지 않는다. 실제 타입 4종은 공유 유형 생성 정책을 유지한다.

제출 직전에 listVirtualMachines로 VM 상태·소유 범위를 다시 읽는다. Stopped·지원되는 일반 VM인지 검사하고, 선택 ID 각각을 같은 소유 범위의 listAffinityGroups(id)로 확인한다. 화면에서 조작된 타 계정 ID도 POST 전에 거부한다. 최종 권한/상태 판정은 기존 백엔드가 계속 수행한다.

## 작업 수명과 완료 계약

새 affinityGroupOperations 유틸리티가 기존 createJobTracker를 조합한다. 기존 전역 pollJob·Kubernetes·AutoScale의 호출은 변경하지 않는다. 추후 AG-03/AG-04는 새 계약을 재사용할 수 있다.

실제 API와 UpdateVMAffinityGroupCmd.getCommandName은 접수 envelope를 `updatevirtualmachineresponse`로 반환한다. 명령 이름을 단순 소문자로 바꾼 envelope를 추측하지 않고 이 계약을 명시하며, 테스트도 실제 응답 이름을 사용한다.

| 상태 | 의미와 제출 제어 |
| --- | --- |
| idle | 조회와 VM 지원 상태가 확인되면 제출 가능 |
| preparing | 최신 VM/선택을 검증, 중복 제출 차단 |
| submitting | POST 전송 중, 중복 제출 차단 |
| pending | 접수된 jobid를 조회, 성공 알림 없음 |
| retrying | GET 실패를 제한적으로 재조회, POST 재전송 없음 |
| succeeded | jobstatus=1 확인 후 성공 알림·부모 갱신·닫기 |
| failed | 명시적 API 거절 또는 jobstatus=2, 실제 사유와 선택 유지, 사용자 재시도 가능 |
| unknown | POST 결과 불명·receipt 누락·GET 재시도 소진, 자동 재전송 없음 |
| timeout | 관찰 시간 초과. Cloud 작업 취소/실패로 단정하지 않음 |
| cancelled | 보안 범위 변경 등으로 관찰이 중단됨. Cloud 작업 취소 API를 호출하지 않음 |

GET 조회 간격은 1.5초, 연속 실패는 최대 3회 재시도(지수 간격), 추적 시간은 120초다. GET/POST HTTP timeout은 각각 15/30초다.
jobid가 있는 unknown/timeout 상태에서는 같은 jobid만 수동 재조회한다. jobid를 받지 못한 결과 불명 상태는 다시 제출하지 못하도록 유지하고 VM/Cloud 작업의 수동 확인을 안내한다.

작업 receipt와 원하는 선택 ID는 현재 앱 세션의 VM별 레지스트리에 남는다. 대화상자를 닫거나 다른 경로로 이동해도 작업 추적은 유지하고 이전 컴포넌트의 성공 알림/갱신은 실행하지 않는다. 다시 열면 같은 작업을 관찰한다. 로그인 토큰·사용자·프로젝트 범위가 달라지면 기존 레지스트리와 관찰을 무효화하고 늦게 도착한 응답을 무시한다. 다음 GET 이전에도 보안 범위를 검사한다.

닫혀 있는 동안 완료된 작업을 다시 열면 완료 receipt의 선택을 복원한 뒤 다음 변경을 허용한다. 이전 컴포넌트에 늦은 성공 알림을 보내거나 POST를 다시 실행하지 않는다.

브라우저 전체 재시작/새로고침을 넘는 receipt 영속화는 이번 범위에 없다. 브라우저 작업 이력은 Cloud 최종 상태의 대체 자료가 아니다.

## UI

- VM 소유 범위 표시, Stopped/지원 여부 안내.
- 후보 조회 오류는 기존 행·선택을 유지하며 재조회 버튼 제공.
- 작업 단계·실패 이유·jobid·수동 재조회 표시. 처리 중 입력/선택/페이지 조작과 중복 제출 차단.
- 결과를 알 수 없는 요청은 실패로 확정하거나 성공 알림을 띄우지 않는다.
- 한글/영문 문구를 함께 추가하며 나머지 언어는 기존 한글 fallback을 유지한다.
- 다중 페이지 선택 보존/검색 페이지 초기화는 #1415, 생성 폼은 #1416, 멤버 탭은 #1417, 전반 외형 정돈은 #1418의 범위로 남긴다.

## 검증 계획

1. 집중 단위/컴포넌트 테스트: 올바른 owner 파라미터·도메인 공유 응답 보존·권한 없는 선택/신선도·최종 실패·정상/빈 목록·조회 재시도·timeout·결과 불명·중복 제출·닫기/다시 열기·보안 범위 변경.
2. 기존 jobTracker와 background job transport 회귀, 변경 파일 lint, UI production build. 전체 Cloud/Maven 빌드는 하지 않는다.
3. 31번에서 admin/새 일반 사용자/새 프로젝트의 전용 그룹·Stopped VM으로 실제 UI 후보·연결/전체 해제·재조회·실패 표시와 API/DB 매핑 검증.
4. WEB-INF/META-INF·config·JAR/PID와 전체 webapp을 백업·보존해 정적 UI만 갱신한다. 배포 파일 해시와 /client/ HTTP 200, Mold active 확인.
5. 전용 자원 활성 잔여 0 및 기존 그룹·VM Affinity 정보 보존 확인. 상세 결과는 AG-01 검증 문서에 별도로 기록한다.

## 구현 결과

31번 정적 UI 배포와 집중 테스트 50개, 실제 admin/일반 사용자/프로젝트/도메인 공유 그룹의 연결·해제, 최종 실패, 조회 통신 오류·닫기/재열기·재조회·후보 재시도를 검증했다. 사용 중인 Ant Design Alert의 action 슬롯이 표시되지 않는 문제는 description 안에 버튼을 배치해 해결하고 실제 Alert/Button 테스트를 추가했다. 상세 범위와 제한, 소스/배포 해시 및 API/DB 정리 증거는 [AG-01 검증 보고서](../../validation/affinity-1414/REPORT.ko.md)에 기록했다.
