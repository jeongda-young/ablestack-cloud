# AG-06 API·UI 통합 및 실제 호스트 배치 검증

대상 #1419 · Epic #1413 · 누적 PR #1420 · 31번 클러스터 · 2026-10-19.

## 검증 소스와 구현

최신 Europa `8c5a92a4d9978229221613f4ff3e36e2df54daeb`를 Epic 브랜치에 병합했다(`a57b608f719`). 이 병합의 추가 7개 파일은 upstream #1379의 스냅샷 복구 백엔드다. Affinity 변경은 UI에 한정하며 해당 JAR을 교체하거나 스냅샷 복구 기능까지 검증했다고 주장하지 않는다. 착수 당시 배포 UI `b5b941ec0fa5c6bd11c054422e4160bc1ec7ef03`에서 실제 생성·역할·배치 경로를 검증하고 결함을 추가 발견했다. 수정 UI `8beac110e7fc497edd9cbf1a1da5b0fd8a329249`를 16:04 KST 배포해 소유자 조회·정책 표시·부분 실패/재시도·삭제·반응형을 재검증했다. 모바일 CSS 보완 후 최종 배포 UI는 `1a5b52159fdc1d7fec97e9daa4afc5acd60bc011`다. `8beac110e7f`와 최종 UI의 template/script는 동일하며 선택기 CSS만 추가 보완했다. 증거를 모두 동일 배포의 결과로 묶지 않는다.

- 공통 VM 생성/백업 복구/VNF/AutoScale Affinity 선택기에 남은 영문 원문 정책을 공통 한글 정책 표시로 통일했다. 알 수 없는 정책은 원문을 유지하고 API 유형·선택 ID는 바꾸지 않는다. 좁은 화면에서는 표 안에서 가로 스크롤한다.
- 도메인 관리자의 타 계정 그룹 최신 조회에 `projectid=-1`을 강제하면 정상 그룹도 빈 결과가 되는 결함을 실제 API/UI에서 재현했다. 일반 그룹의 멤버·삭제 영향 조회는 실제 계정/도메인 또는 프로젝트를 사용한다. ExplicitDedication 공유 그룹은 도메인의 여러 계정/프로젝트를 포함할 수 있으므로 전체 프로젝트·재귀 범위를 유지한다.
- 서버의 권한 판정을 바꾸지 않았다. 도메인 관리자는 자기 계정 그룹을 생성·연결할 수 있지만 타 계정 그룹 연결 변경은 서버가 531로 거절한다. 이를 성공으로 집계하거나 UI에서 우회하지 않는다.

각 선행 보고서에는 수정 전 실패와 수정 후 실제 UI/API/DB 근거, 배포 artifact 해시가 남아 있다. 이번 최종 집중 회귀는 **23 suites / 318 tests**이며 기존 실패/timeout/결과 불명·조회 실패/응답 경합·일부 성공 재시도·소유자 전환 보호를 포함한다. 이 근거를 새로운 실환경 장애 주입 건수로 재집계하지 않는다.

착수 UI에서는 12개 선택·다음 페이지·단일 검색 후 숨겨진 12개 보존·전체 해제·하나 선택을 실제 VM 마법사로 수행했다. 엄격 Affinity를 선택한 `qa-ag06-ui-vm-01`이 생성·시작되어 UI·API·DB·실제 도메인에 같은 그룹과 호스트가 반영됐다. Running VM의 개별 변경 메뉴는 제공되지 않고 멤버 선택도 제한 사유와 함께 비활성화됐다. 자동 정지는 없었다.

중복 이름의 API 오류 후 생성창·이름/설명/유형·초점이 유지됐고 이름 수정 후 생성이 완료됐다. 고급 검색에는 이름/유형/도메인/계정/프로젝트만 있으며 Zone은 없다. 프로젝트 그룹 관련 VM 이동의 이름 필터와 프로젝트·Back·활성 탭, 진행 중 결과창을 닫은 뒤 최종 영수증 재열기를 확인했다.

## 실제 호스트 배치와 보장 범위

착수 시 KVM 3대 모두 Up/Enabled, 각 96 CPU, CPU 할당 44.53~49.48%, 메모리 총 약 502 GiB였다. 공유 Primary는 Up·`glue-gfs`, 총 약 21.83 TiB/할당 약 9.92 TiB였다. 운영 VM/호스트를 정지하거나 물리 용량을 고갈시키지 않았다. 전용 VM만 시작·정지했다.

각 체크포인트는 API의 VM UUID/상태/host UUID/그룹 목록을 DB의 VM·host·매핑과 비교하고, 3개 하이퍼바이저에서 `virsh list --name --state-running`의 해당 도메인이 정확히 한 곳에서 실행되는지 대조했다. DB 행만으로 실제 실행을 판정하지 않았다.

| 유형/조건 | 관찰한 결과 | 판정과 한계 |
| --- | --- | --- |
| 엄격 affinity | UI 생성 VM과 UI 연결한 두 번째 VM이 모두 `ablecube31-2`에서 Running | 동일 호스트 배치 확인. 다른 호스트를 지정한 세 번째 시작은 job 실패, Stopped 유지 |
| 엄격 anti-affinity | 첫 3개가 `31-2 / 31-1 / 31-3`에 분산 | 네 번째 시작은 실패, 기존 3개는 보존. 물리 용량 고갈이 아니라 정책상 사용 가능한 독립 호스트 수 소진 |
| 선호 affinity | 첫 VM을 `31-1`로 지정한 뒤 두 번째 자동 시작도 같은 호스트에 배치, 세 번째의 명시적 `31-2` 지정도 성공 | 선호는 강제 제약이 아님을 확인 |
| 선호 anti-affinity 신규 배포 | 새 그룹의 신규 VM 두 개는 `31-3 / 31-2` | 신규 VM의 정상 분산 사례 확인 |
| 선호 anti-affinity 기존 VM 재시작 | 4개 모두 Running, 배치는 `31-1 / 31-1 / 31-2 / 31-3` | 첫 3개가 항상 분산된다는 시험 가정은 실패. 원래 실패 로그를 보존했고 PASS로 바꾸지 않았다 |
| 선호 anti-affinity 명시적 충돌 | 네 번째 VM을 첫 번째 VM의 `31-1`로 지정해 시작 성공 | 동일 호스트 허용 확인. 재시작/자원 제약에서도 분산을 보장한다는 주장 불가 |

엄격/선호의 실제 관찰은 구별한다. CPU·메모리·스토리지의 물리적 고갈, 호스트 장애/격리, 다중 Zone, 동시 대규모 시작은 미검증이다. 선호 정책의 재시작 시 우선순위 이유를 이 결과만으로 단정하지 않는다. 기존 이력을 가진 VM과 신규 VM 시험은 별개다.

## 역할·공유·소비자

관리자·일반 사용자·프로젝트·도메인 관리자·list-only 제한 역할로 실제 UI에 로그인했다. 일반 사용자는 자신의 그룹과 사용 가능한 도메인 공유 그룹만 봤고 UI 연결→공유 그룹 추가→전체 해제의 최종 결과를 확인했다. 프로젝트 그룹 연결 후 관련 VM 조회/Back/영수증 복원을 거쳐 그룹을 UI에서 삭제했고 VM이 Stopped로 보존됐다. 제한 역할에는 생성/삭제 동작이 없고 멤버 변경 버튼이 비활성화되며 타 계정 직접 상세 URL은 대시보드로 이동했다. 별도 API 생성 요청도 432로 거절됐다.

도메인 관리자의 자기 계정 그룹 생성·자기 VM 연결은 최종 성공했다. 타 계정 그룹 읽기와 쓰기는 다르며 쓰기는 서버가 거절한다. 이 거절을 역할 경로의 성공적인 연결 변경으로 집계하지 않는다. 일반 배치 4개 유형은 도메인 공유 생성이 거절됐고, 관리자 제어 `ExplicitDedication` 빈 그룹의 공유 조회·연결은 지원됐다. 호스트/클러스터/Zone 전용화는 수행하지 않았다. Affinity 목록 API에는 Zone 필터가 없다.

AutoScale 마법사의 공통 선택기 조회·선택 요약, Kubernetes 생성의 역할별 후보 검색·선택을 실제 UI에서 확인하고 제출 없이 취소했다. Kubernetes/AutoScale 클러스터·LB·증감 시나리오 전체 합격을 주장하지 않는다. 현재 서버는 `listBackups`/`listBackupProviders`를 Unknown API로 거절하고 VNF 템플릿 조회도 빈 결과다. 백업/VNF 전체 생성은 실환경 미검증이며 공통 부모 선택·범위 전환·실패 데이터 보존은 집중 테스트로 검증했다.

## 배포 후 최종 판정

수정 `8beac110e7f` 배포에서 893개 정적 파일 해시·서버 보존·Mold active·HTTP 200을 확인한 뒤 기능을 검증했다. 멤버 2개를 선택한 후 외부 API로 하나를 Running으로 바꿨을 때 첫 VM만 성공하고 두 번째는 Stopped 조건 사전검사에서 실패했다. 해당 VM을 정지한 뒤 UI의 “최신 상태 확인 후 실패만 재시도”로 두 번째만 새 작업을 제출했다. 첫 VM의 성공 작업 ID는 그대로 유지됐고, 최종 두 VM에 대상 그룹과 기존 선호 그룹이 함께 남았다. 원래 부분 실패와 명시적 복구를 구별한다.

삭제창의 최초 영향은 VM 1개였다. 외부 연결 변경으로 2개가 된 뒤 첫 삭제 클릭은 재확인 안내와 영향 2개 갱신만 수행했고 삭제 POST가 없었다. 두 번째 명시적 클릭 후 그룹만 제거됐으며 두 VM은 Stopped, 다른 두 그룹 연결은 보존됐다. UI 작업 12개의 최종 성공 영수증은 DB `async_job.job_status=1`과 대응했다. 중복 생성·권한 거절·부분 실패·엄격 정책 시작 실패를 이 12건의 성공 수에 섞지 않았다.

1440×900·390×844·390×480에서 라이트/다크 각 7개 화면, 총 42개 레이아웃 상태를 측정했다. 좁은 화면 캡처의 렌더링 제약 때문에 에뮬레이션은 DOM 좌표·스크롤 폭/높이와 실제 조작으로 판정하고, JPG 시각 확인은 기본 브라우저 viewport에서 수행했다. 390×480의 모달 하단 버튼은 y=467 안에 있고 본문은 내부 스크롤한다. 모바일 탭은 정보 카드 아래에 있으므로 세로 스크롤한 뒤 클릭할 수 있으며, 고정 헤더가 클릭을 가로채지 않았다.

모바일 VM 마법사에서는 256px 선택기에 공통 `min-width:500px` 표 본문이 넘쳤다. 첫 CSS 수정 `8588368d2d4`도 공통 모바일 규칙의 specificity에 밀려 재측정에 실패했다(`first-mobile-fix-insufficient.json`). 최종 `1a5b52159fd`는 선택기 내부 최소 너비만 우선 적용한다. 이 첫 실패를 최종 합격으로 바꾸지 않는다.

최종 UI `1a5b52159fd`를 **16:38:33 KST**에 배포했다. 최종 선택기 6개 화면을 다시 측정했고 라이트/다크의 390px 화면에서 선택기 `clientWidth=scrollWidth=256`, 본문 `clientWidth=246 / scrollWidth=640`, 계산된 `min-width=0px`·`overflow-x=auto`였다. 선택기 밖 넘침 없이 내부 가로 스크롤이 유지됐다. 선택 요약·한글 정책 표시·Enter 전체 해제를 다시 확인했다. 최종 UI의 멤버 탭은 Running VM 2개와 `31-3 / 31-2` 호스트, 변경 제한을 표시했고 이벤트 탭은 해당 그룹의 AG.CREATE 2개 기록을 조회했다.

## 남은 문제와 Epic

도메인 공유 그룹을 포함하는 도메인 관리자 `listAffinityGroups`가 실제 고유 그룹 4개에 `count=5`를 반환한다. `pagesize=2`의 1/2페이지는 각 2행이고 3페이지는 0행이다. 자기 계정 그룹을 UI에서 삭제한 후에도 실제 3개 행에 count=4가 남았다. UI 조회 범위 수정과 구별되는 서버 count/페이지 결함이며 [별도 AG-07 #1421](https://github.com/ablecloud-team/ablestack-cloud/issues/1421)에서 수정한다. 이 상태를 전체 기능 무결함이나 Epic 완료로 보고하지 않는다.

마지막 조회와 전체 그룹 교체 사이의 CAS 없는 경합, 앱 재로드를 넘지 못하는 메모리 영수증은 기존 계약의 한계다. 이번 범위에서 백엔드 계약 확장을 구현했다고 주장하지 않는다. 전체 Cloud/Maven 빌드·전체 Actions CI는 실행하지 않았고, 등록 체크 없음은 전체 CI 합격이 아니다. Epic PR은 누적 Draft를 유지하며 병합하지 않는다.
