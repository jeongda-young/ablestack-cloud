Import and payload

Select a UTF-8 text file or an explicitly Base64-encoded file in registration. The preview shows the actual payload as original content or Base64. Apply to content explicitly replaces the draft; cancellation or invalid files preserve it.

Text imports preserve Korean, UTF-8 BOM, CRLF/LF and trailing newlines byte for byte. Applied content uses Base64 with the Base64 input option selected to preserve these bytes. Base64-looking text imported as text remains literal text. Base64 files must be UTF-8/ASCII text; spaces, tabs, CR and LF are normalized. A BOM in a Base64 file is rejected. UTF-16 and invalid UTF-8 are not guessed or converted.

The server limit applies to normalized Base64 length. Import and registration share validation. Empty, whitespace-only and oversized payloads are rejected. Archives, remote URL imports and script execution are not provided.

Minimal formats

Cloud-config:

#cloud-config
write_files: []
runcmd: []

Supported Jinja cloud-config header:

## template: jinja
#cloud-config
write_files: []
runcmd: []

These format examples do not install a network plugin. Prepare installation content for the Kubernetes version, node image and network. A standalone Kubernetes manifest is not applied automatically. Other existing cloud-init formats such as shell depend on the guest and provider path. This UI stores content and does not establish execution success.

Variables and scope

Add parameter names explicitly and confirm each with Enter, for example POD_CIDR. Names start with a letter or underscore and then permit letters, digits, underscores, dots and hyphens. Duplicate and reserved metadata names are rejected. Import does not extract or substitute variables.

Select the same-scope CNI in the Kubernetes wizard and enter its declared values. For non-Jinja source, the server literally replaces declared simple {{ NAME }} tokens, including repeated and adjacent tokens. Values are not evaluated again. A leading backslash in \{{ NAME }} preserves the token as literal text and removes that escape. Undeclared tokens stay unchanged and are reported as unresolved. Missing declared values and extra values are rejected before provisioning; an explicitly empty string is a value. Authors must prepare escaping appropriate for their YAML or shell context. With a Jinja header, ordinary expressions such as {{ ds.meta_data.NAME }} are preserved for the guest metadata path and are not executed by the server preview. AS_NUMBER is automatic, with the exact special server token {{ AS_NUMBER }}. Use Extract variables to review and apply candidate names, and Preview substitutions in the Kubernetes wizard to inspect the server payload and missing, extra or unresolved values. An AS number not yet allocated remains pending.

CNI configurations are distinct from the VM UserData library. Account, domain and project access rules apply. Kubernetes references prevent deletion. Registering new content does not automatically change running clusters.

Cloning and clone history

Use Clone CNI configuration to register a new name, body and declared variables in the same owner scope. The source and existing Kubernetes clusters are unchanged. If a registration response is lost, check the registration result first. If registration succeeds but the source relationship is not saved, retry only the relationship record.

Clone history shows the current configuration, its sources and derived configurations. Compare with source, or select two accessible configurations and compare them, to inspect body bytes, variable declarations and changed regions without changing data. Declared variables are distinct from values used by a running cluster. Non-UTF-8 content supports byte comparison, Base64 and download, but no text diff. Changed regions display at most 500 lines and 65,536 characters; expand the full bodies separately.

Relationship records are editable, deletable advisory information. Deleted or inaccessible sources, invalid or cyclic records and failed reads have distinct states. Lookup covers at most 200 configurations in the owner scope and 16 source steps, in addition to the direct current-configuration lookup. A scope-limit or unverified-record warning means the results are not a complete history. Configurations with many comments may reach the relationship lookup limit. Comparison does not roll back or replace a cluster CNI.
